# Тестування SlideSync Local

## Команди

Після `npm ci`:

```sh
npm test
npx playwright install chromium webkit
npm run test:browser
```

`npm test` використовує вбудований Node.js test runner. Сервери запускаються на випадкових портах і зупиняються після тестів. Більшість тестів працює через `127.0.0.1`; одна перевірка навмисно слухає всі IPv4-інтерфейси й звертається до LAN-адреси цього самого ноутбука, щоб перевірити розмежування доступу. За відсутності LAN-інтерфейсу ця перевірка пропускається.

Playwright запускає по сім наскрізних сценаріїв у Chromium і WebKit із мобільними налаштуваннями iPhone. Сам ведучий у головному сценарії має розмір вікна ноутбука; переглядачі — мобільні вікна. Тести не звертаються до інтернету. Першочергове встановлення пакетів і браузерів потребує інтернету.

Середовища з пісочницею можуть забороняти відкриття портів або запуск браузера. Помилка `listen EPERM` у такому середовищі означає обмеження оточення; повторіть тест у звичайному локальному терміналі з дозволеним локальним сервером.

## Автоматичні серверні перевірки

1. Відсутній/неправильний ключ перегляду, неправильний ключ ведучого, сторонній Origin і Host; некоректний Unicode у ключі не має аварійно завершити сервер.
2. Справжній PDF конвертується у п’ять JPEG; перевіряються розміри, сигнатура, декодування та загальний обсяг. Доступ до JPEG потребує ключа; некоректні номери дають 404.
3. Двадцять п’ять WebSocket-клієнтів одержують поточний deck і однаковий новий індекс. Готовність кешу враховується, учасницькі команди не змінюють слайд. Новий клієнт бачить поточну позицію.
4. Від’ємний індекс, вихід за межі, дробове/текстове/null значення, застарілий deckId відхиляються.
5. Не-PDF, пошкоджений PDF і 151 сторінка не знищують поточну презентацію.
6. PDF зі стандартним шифруванням дає повідомлення про пароль. Тест використовує мінімальну синтетичну зашифровану структуру; різні реальні PDF-редактори слід перевірити окремо.
7. Два паралельні завантаження серіалізуються: друге отримує 409. Успішна заміна скидає позицію і готовність; старі URL недоступні.
8. Файл понад 40 МіБ отримує 413, додаткові multipart-поля відхиляються. Після завершеної відповіді блокування upload уже звільнене.
9. WebSocket зі стороннім Origin, ключем перегляду в ролі ведучого та невалідним ключем відхиляється.
10. Примусовий timeout Worker не блокує сервер і не активує часткову презентацію.
11. Поворот сторінки на 90° дає JPEG 900 × 1600; українське ім’я PDF зберігається.
12. Через справжню LAN-адресу ноутбука дозволено авторизований перегляд, але заборонено пульт, host API і host WebSocket, навіть із правильним ключем ведучого.

Після штатного закриття сервера перевіряється, що його тимчасова папка видалена.

Окремо перевіряється передавання незавершеної лінії через WebSocket, завершення й збереження постійного малюнка, заборона змін від учасника, очищення через HTTP, відхилення старого epoch та очищення після зміни слайда/PDF. Файл `annotations.test.mjs` перевіряє інструменти, координати, тиск, атомарне відхилення неправильних даних, ліміти та видалення тимчасової лінії через 5 секунд зі збереженням постійної. Додаткові перевірки фіксують непрозорість до, всередині та після згасання й відсутність стрибка яскравості при ручному очищенні.

## Наскрізні браузерні перевірки

Кожний сценарій виконується у Chromium і WebKit:

1. Відкриття пульта і переглядача до PDF; завантаження PDF через форму; повне кешування у двох мобільних вкладках; правильні лічильники; синхронне перемикання; відсутність повторного JPEG-запиту для кешованого слайда; розрив/відновлення мережі; повернення до актуального слайда; перезавантаження вкладки з ключем із sessionStorage; заміна PDF; відсутність необроблених JavaScript-помилок.
2. Штучне блокування WebSocket: HTTP-опитування продовжує оновлювати слайд, попередньо завантажує JPEG і передає малюнки. Перехід в історію та повернення до актуального кадру не втрачають шар малювання.
3. Посилання учасника без ключа показує зрозумілу інструкцію відсканувати QR.
4. Малювання справжніми діями миші: усі три інструменти й різні розміри, видимі пікселі Canvas на телефоні, зміна розміру вікна, очищення, таймер 5 секунд, перехід уперед і назад без відновлення малюнків. Перевіряється проміжний кадр із прозорістю між початковою й нульовою — згасання не можна замінити затримкою з різким видаленням.
5. Два учасники: один самостійно переглядає історію, інший слідує за ведучим. Історія не змінює серверний індекс, не показує малюнки іншого кадру та залишається на обраному слайді. Кнопка повернення відновлює слідування; новий PDF скидає особисту навігацію.
6. Портретний PDF: натискання в чорному полі не малює, натискання в центрі JPEG дає нормалізовані координати приблизно 0,5/0,5.
7. Штучно затриманий JPEG історичного кадру: після повернення до показу завершення старого запиту не замінює поточний слайд запізнілим зображенням.

Скріншоти з головного сценарію створюються в `test-results/`; trace зберігається при помилці. Папка ігнорується системою контролю версій. Фінальні зразки інтерфейсу можуть бути додані до `docs/images/` окремо від тестових тимчасових файлів.

## Результати реалізації

Протокол фінального запуску наведено в `VALIDATION.md` у цій папці. Він відокремлює реально виконані перевірки від ручних пунктів, для яких потрібні фізичні телефони та конкретна Wi-Fi-мережа.

## Ручне приймання на пристроях

Цей чеклист потрібно виконати до першого реального виступу. Playwright WebKit не відтворює системні дозволи, енергозбереження, Wi-Fi та всі обмеження фізичного iPhone.

| Перевірка | Дії | Очікуваний результат |
| --- | --- | --- |
| iPhone / Safari | Сканувати QR системною камерою, відкрити у Safari | Поточний кадр без встановлення застосунку |
| Android / Chrome | Повторити з Android | Той самий кадр, зрозумілий статус |
| Два різні телефони | Дочекатися повного кешу, перемкнути 10 слайдів | Обидва слідують за ведучим, без повернення до старого кадру |
| Без інтернету | Від’єднати WAN роутера, залишивши LAN/Wi-Fi | QR, слайди та синхронізація працюють |
| Кешування | Дочекатися «Усі … слайдів завантажено» | Пульт враховує готовність, уже кешовані слайди не потребують повторного завантаження |
| Розрив Wi-Fi | На телефоні вимкнути Wi-Fi, змінити слайд, увімкнути Wi-Fi | Старий кадр не зникає; після відновлення показується актуальний |
| Фон і блокування | Заблокувати iPhone на 30–60 секунд, змінити слайд, повернутися | Оновлюється поточний стан, без ручної навігації |
| Поворот | Портретний і альбомний режими | Слайд повністю видимий, пропорції збережені |
| Fullscreen | Натиснути «Розгорнути» | Fullscreen або зрозуміла порада про альбомний режим |
| Великий PDF | Власна презентація близько до реального обсягу | Коректні шрифти/зображення; прийнятний час preload і споживання пам’яті |
| Заміна | Під час показу завантажити новий PDF | Старий показ працює до готовності; потім усі бачать перший новий слайд |
| Малювання | Увімкнути малювання, обрати олівець/пензлик/маркер, різні розміри та колір | Учасники бачать однаково розташовані лінії поверх слайда |
| Час малюнка | Намалювати в режимах «5 секунд» і «До очищення» | Тимчасове зникає через 5 секунд, постійне лишається до очищення/переходу |
| Зміна слайда з малюнком | Перейти вперед, потім назад | На обох кадрах немає попередніх малюнків |
| Історія на телефоні | Повернутися на попередній слайд, перемкнути пульт, натиснути «До поточного слайда» | Особистий кадр лишається обраним до повернення; після повернення слідує за ведучим |
| Повноекранне малювання | Розгорнути пульт, обрати інструмент і малювати | Панель доступна; JPEG і лінії не зміщуються |
| Невдалий PDF | Завантажити пошкоджений/захищений файл | Помилка в пульті, старий показ доступний |
| Гостьова мережа | Увімкнути/перевірити client isolation | За блокування зв’язку обрати мережу без ізоляції; це не виправляється браузерним кодом |
| Мережеві адреси | VPN увімкнений; обрати Wi-Fi IPv4 у пульті | QR містить доступну телефонам адресу |
| Перезапуск | Ctrl+C, знову npm start | Старий ключ недійсний, новий QR працює, PDF потрібно завантажити знову |

Для перевірки відсутності зовнішніх запитів відкрийте Network у засобах розробника браузера ноутбука: усі ресурси застосунку мають надходити з адреси локального сервера. Окремі системні звернення самого браузера не є запитами SlideSync Local.

## Перевірка місткості Wi-Fi

Автотест 25 сокетів перевіряє серверний протокол, а не реальні радіоканали. Для великої групи виміряйте preload на реальній кількості телефонів. Наприклад, презентація JPEG обсягом 10 МіБ на 25 телефонах потребує близько 250 МіБ сумарної передачі без урахування протокольних накладних витрат. Вузьким місцем зазвичай буде одночасне початкове завантаження, а не невеликий JSON при перемиканні.

Почніть із двох телефонів, потім перевірте цільову групу. Фіксуйте час приєднання, повного кешування, реакції на слайд і відновлення зв’язку. Якщо Safari вивантажує вкладку, зменште PDF або розділіть презентацію; ліміт 48 МіБ JPEG не є гарантією допустимого обсягу пам’яті на кожному iPhone.
