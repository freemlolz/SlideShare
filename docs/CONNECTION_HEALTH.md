# Стан учасників

Панель «Стан учасників» у правій колонці пульта автоматично показує відомі серверу профілі браузерів. Телефони не отримують цю панель або список інших учасників.

## Що означають стани

| Стан | Умова |
| --- | --- |
| Підключено | Принаймні один WebSocket профілю підтвердив зв’язок менш як 25 секунд тому |
| HTTP-резерв | Немає свіжого WS, але є авторизований HTTP-запит менш як 10 секунд тому; після закриття останнього сокета потрібен новий HTTP-запит |
| Відновлює зв’язок | Свіжого транспорту немає, але від останнього контакту минуло менш як 35 секунд |
| Від’єднано | Від останнього контакту минуло щонайменше 35 секунд |

Сервер перевіряє зміни станів раз на 2 секунди; приватні оновлення пульта об’єднуються протягом 250 мс. Це приблизна оцінка доступності, не діагностика причини збою. Сон телефона, фонова вкладка, збій Wi-Fi та вимкнений пристрій можуть виглядати однаково.

Верхні метрики «WS-вкладок» і «готових WS-вкладок» зберігають попереднє значення: кількість відкритих WebSocket, не унікальних профілів. Тому дві вкладки одного браузера дають дві WS-вкладки, але один запис у новій панелі.

## Ідентичність і збереження

- Використовується вже наявна підписана сервером cookie учасника. Нові акаунти, fingerprinting, IP-адреси й назви пристроїв не потрібні.
- Підтверджена cookie необхідна для обліку. Клієнт без cookie може читати слайди через HTTP, але його запити не створюють щоразу нових «учасників».
- Написи «Учасник 1», «Учасник 2» тощо — послідовні анонімні мітки. Один профіль із кількома вкладками об’єднується; закриття однієї вкладки не від’єднує інші.
- Повторне приєднання з тією самою cookie відновлює запис і мітку. Інший браузер, приватне вікно, інша адреса ноутбука або очищення cookie можуть створити інший запис.
- Відомі від’єднані записи залишаються до кінця запуску або кнопки «Прибрати запис». Сервер забороняє прибирати ще активний запис. Якщо видалений профіль знову подає ознаки зв’язку, він отримує нову мітку.
- Межа — 500 записів, включно з від’єднаними. Коли місця немає, ведучий має прибрати старі записи; сервер відмовляє новим замість необмеженого накопичення даних.
- Реєстр лише в пам’яті. Перезапуск прибирає записи й створює нову сесію. Експорту, журналу відвідування та обліку людей немає.

## Прогрес слайдів

Для здорових WS-вкладок показується найбільше завантаження активної вкладки цього профілю. Це означає «принаймні одна вкладка», не готовність кожної вкладки. Нова вкладка/перезавантаження без інших готових вкладок починає з нуля.

В HTTP fallback клієнт надсилає останній прогрес до `POST /api/ready?token=…`. Запити послідовні; проміжні звіти можуть об’єднуватися, невдалий повторюється. Після втрати WebSocket останній звіт переходить на HTTP. Якщо один профіль має кілька HTTP-вкладок, показується їхній останній отриманий звіт, а не гарантія готовності всіх вкладок.

Новий PDF має інший `deckId`, тому готовність старої презентації не переноситься. Для від’єднаного профілю показується останній відомий прогрес поточної презентації. Дані не доводять, що телефон досі тримає весь кеш у пам’яті.

## API й межа приватності

Поле `presence: {totals, participants, limit}` додається лише до авторизованих знімків ведучого через HTTP/WS, heartbeat і відповіді команд. Сервер ніколи не додає його в знімки учасників, зокрема при голосуванні та reconnect. Cookie-ідентифікатор не входить навіть до приватного списку: у ньому є лише окремий числовий ID запису, мітка, стан, транспорт, lastSeen, кількість сокетів і прогрес.

- `POST /api/ready?token=…`: `{deckId, loaded}`, лише учасник із cookie. `loaded` — ціле від 0 до кількості сторінок поточного PDF. Старий deck дає `409`, неправильний прогрес — `400`. Відповідь — `{ok:true}`, без списку учасників.
- `POST /api/host/presence/remove`: `{id}`, лише loopback + `X-Host-Token`. Активний запис — `409`, невідомий — `404`.

HTTP/WS залишаються незашифрованими; ця панель не змінює вимогу довіреної LAN. Якщо стороння програма захоплює весь екран пульта, вона захопить і панель. Для зовнішньої трансляції відкривайте окреме вікно учасника.

## Перевірка

```sh
npm test
npm run test:browser -- test/browser/presence.spec.mjs
```

Автоматизація перевіряє межі таймерів, об’єднання вкладок, відновлення мітки, прогрес різних транспортів, заміну PDF, обмеження пам’яті, видалення записів і відсутність списку в HTTP/WS учасника. Chromium і WebKit перевіряють приватну панель, дві вкладки одного профілю, HTTP fallback, готовність, від’єднання та повторне приєднання.

Фізичні iPhone/Android потребують ручної перевірки: згорніть браузер, заблокуйте екран, вимкніть Wi-Fi більш як на 35 секунд, поверніться у вкладку та перевірте відновлення того самого запису. Нова серверна функція потребує перезапуску Node.js, не лише оновлення сторінки; поточний PDF і QR при цьому скидаються.
